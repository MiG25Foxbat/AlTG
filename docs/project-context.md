# Контекст проекта: Telegram AI-алертер

Этот файл — расширенная версия истории проекта для тех случаев, когда нужен
полный бизнес- и архитектурный контекст, а не только текущее состояние кода
(которое описано в корневом `CLAUDE.md`). Читать по необходимости, не при
каждой сессии.

## Идея и бизнес-контекст

Продукт — Telegram-бот, который мониторит публичные (и в перспективе
приватные) Telegram-каналы, фильтрует посты по теме, которую задаёт
пользователь, и присылает саммари через ИИ вместо того, чтобы пользователь
читал десятки каналов вручную.

Целевые сегменты (ICP), под которые уже готовились опросники, интервью-скрипты
и outreach-шаблоны на русском языке:

1. Крипто-трейдеры
2. Трейдеры на традиционных рынках
3. Владельцы малого/среднего бизнеса
4. PR/маркетинг-специалисты
5. Инвестиционные аналитики

Выбранный go-to-market — B2B-уклон. Как самая низкорисковая стартовая точка
выбран простой алерт-MVP только по публичным каналам через Bot API/чтение
(без приватных каналов и юзербот-специфики на старте).

## Ключевое ограничение, действующее на весь проект

Всё технологическое решение — от хостинга до модели ИИ — выбирается по
критерию: **самое дешёвое, вплоть до полностью бесплатного, при условии, что
оно надёжно работает и не является заведомо устаревшим**. Не самое модное,
не "как у всех", а самое дешёвое из надёжно работающих. Это правило
применяется и к выбору модели ИИ, и к хостингу, и к библиотекам.

Отдельно велась ревизия предложенного техстека (TGStat-based) на соответствие
этому правилу — см. `docs/tech-stack-review.md`. Вывод той ревизии: часть
предложенных инструментов была объективно устаревшей или платной там, где
есть бесплатная альтернатива того же качества.

## Целевая архитектура (из более раннего планирования — НЕ то, что сейчас реализовано)

Это архитектура, которая обсуждалась и планировалась для полноценного
продукта, до того как было решено собрать быстрый прототип для тестирования
на GramJS-коде gram-pervonah. Текущий прототип (см. корневой `CLAUDE.md`)
сознательно проще и не следует этому плану — это временное упрощение для
проверки гипотезы, а не отказ от плана.

- **Рантайм:** Bun (не Node/ts-node, как в текущем прототипе)
- **Telegram-слой:** гибридный подход — публичные каналы читаются через RSS
  (RSSHub), приватные каналы — через MTProto-юзербот (GramJS/Grammy)
- **Фильтрация:** трёхслойный пайплайн для резкого снижения затрат на ИИ:
  1. Строчный (keyword) матчинг — бесплатно, отсекает явно нерелевантное
  2. Семантические эмбеддинги — дёшево, отсекает то, что не прошло keyword,
     но может быть релевантно по смыслу
  3. LLM — дорого, применяется только к тому, что прошло первые два фильтра
- **ИИ-модели:** Groq + Gemini (комбинация; конкретная модель зависит от
  задачи и стоимости на момент использования)
- **Хостинг:** Railway + SQLite (не Render — Render появился позже как
  экстренное решение конкретно для прототипа, см. корневой CLAUDE.md)
- **Юзербот, детали:**
  - Health-check сессии не отдельными вызовами, а по типам ошибок,
    возникающих в обычном цикле чтения (дешевле, естественнее)
  - Анти-бан меры: резидентные прокси, спуфинг имени устройства,
    рандомизированный джиттер между опросами
  - Magic-link реавторизация для пользователей (не пароль/сессионная
    строка вручную)

Когда прототип на текущем стеке подтвердит гипотезу (что двухступенчатая
фильтрация + одна модель дают приемлемое качество саммари за разумные
деньги), имеет смысл either портировать проверенную бизнес-логику на
целевую архитектуру, either осознанно оставить упрощённую версию, если она
окажется достаточной — это открытый вопрос, а не решённый.

## История разработки (хронология по сессиям)

1. Получены и проверены MTProto API credentials (через аккаунт друга),
   рабочий скрипт авторизации GramJS.
2. Проведена подготовка к валидации спроса: ICP-исследование, опросники,
   интервью-скрипты, outreach-шаблоны для всех пяти сегментов.
3. Решена локальная dev-проблема: проект внутри OneDrive ломал `npm install`
   — перенос на `C:\` решил.
4. Исправлено несоответствие: агент по умолчанию предлагал Next.js вместо
   чистого Bun-воркера — поправлено под целевой стек.
5. Ревизия стороннего техстека (TGStat-based) на соответствие правилу
   "дешевле-надёжнее-не устарело" — см. `docs/tech-stack-review.md`.
6. **Текущий этап (сентябрь 2026):** решено не строить сразу полную целевую
   архитектуру, а взять готовый GramJS-юзербот `github.com/litury/gram-pervonah`
   (изначально бот для авто-реакций/авто-комментариев) и переделать его в
   быстрый прототип: чтение постов → фильтр по теме → саммари через
   `gemini-3.1-flash-lite`, без трёхслойного пайплайна, чтобы посмотреть,
   как работает программа "как есть", прежде чем усложнять.
7. Прототип собран, протестирован (28/28 автотестов), обкатан на Windows
   (упёрлись в нативную сборку `better-sqlite3` — решено переходом на
   встроенный `node:sqlite`).
8. Задеплоен на Render (бесплатный тариф) — понадобилось, потому что Gemini
   API недоступен с российских IP, а Render даёт сервер за пределами РФ.
9. Пользователь подтвердил: всё перенесено на Render, установлено,
   протестировано, все функции работают.
10. Принято решение перевести дальнейшую разработку в Claude Code (эта
    сессия/чат — не тот инструмент, которым проект будет вестись дальше).
    Отсюда — этот файл и корневой `CLAUDE.md`.

## Важно про модель gemini-3.1-flash-lite

Пользователь явно просил подтвердить, что это оптимальный выбор с учётом
всего контекста проекта (бесплатность/дешевизна, надёжность, отсутствие
устаревания). Вывод на момент выбора: модель подходит под задачу
(суммаризация + relevance-фильтр по короткому/среднему тексту, окно
контекста с большим запасом на пачку постов), но у нее есть системное
ограничение, не зависящее от качества модели самой по себе: Gemini API
недоступен из РФ на уровне сети. Отсюда и необходимость Render/любого
не-российского хостинга — это не временный костыль, а постоянное
архитектурное ограничение, пока проект использует Gemini.
