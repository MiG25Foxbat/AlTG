# Финальный технологический стек и архитектура данных

Этот документ фиксирует принятые решения по стеку проекта и подробную
архитектуру базы данных для перехода к многопользовательской модели
(каждый конечный пользователь подключает свой Telegram-аккаунт, чтобы
алерты работали и по приватным каналам). Документ самодостаточен и
адресован разработке — включая Claude Code — как источник истины по
принятым решениям. Общий бизнес-контекст и история — в
`docs/project-context.md`, текущее состояние собранного прототипа — в
корневом `CLAUDE.md`.

## 2. Рантайм и хостинг приложения

Без изменений относительно текущего прототипа: Node.js + Express на
Render. Это решение уже проверено в проде и укладывается в правило
"дешевле-надёжнее-не устарело" — менять нет причины.

Важная оговорка на будущее (не блокирует текущий этап): бесплатный
Render-инстанс засыпает после ~15 минут без HTTP-трафика. Пока продукт
работает по запросу пользователя (открыл — нажал — получил дайджест),
это не проблема. Если позже добавляется проактивная фоновая рассылка
алертов (без действия пользователя), бесплатный Render-веб-сервис для
этого не подходит — фоновый цикл опроса каналов будет останавливаться
вместе с засыпанием процесса. Это решается либо платным instance
type с постоянной работой, либо отдельным background worker'ом —
решение по этому пункту сознательно отложено до момента, когда
проактивные алерты станут реальной задачей.

## 3. Telegram-интеграция: переход с GramJS на teleproto

**Решение: заменить зависимость `telegram` (GramJS) на `teleproto`.**

Причина — не предпочтение, а факт: репозиторий `gram-js/gramjs` заархивирован
владельцем 14 июля 2026 года и переведён в режим read-only. Официальное
уведомление в репозитории указывает продолжение разработки в `teleproto` —
активно поддерживаемом форке, декларируемом как обратно совместимый: те же
публичные API, тот же формат session string (включая совместимость со
строками сессий Telethon), миграция — замена импорта `"telegram"` на
`"teleproto"` в большинстве случаев. Отдельно у форка более новый TL-layer
(228) и переписанное сетевое ядро.

Что нужно сделать при миграции (для исполнителя в Claude Code):
1. `npm uninstall telegram && npm install teleproto`.
2. Заменить импорты `from "telegram"` (и подпути `/sessions`, `/events`,
   `/errors`, `/tl`) на `from "teleproto"`.
3. Прогнать `tsc --noEmit` — новый TL-layer может ужесточить типы отдельных
   запросов/ответов.
4. Заменить `sendReadAcknowledge` на `markAsRead` (сигнатура другая: id
   сообщения — позиционный аргумент, `clearMentions` переехал в объект
   опций). В текущем прототипе методы реакций/комментариев закомментированы,
   поэтому вероятность реального использования этого метода низкая, но
   проверить стоит.
5. Логика авторизации и хранения session string не меняется — она была
   спроектирована как GramJS-совместимая, и teleproto читает те же строки.

Сама модель интеграции не меняется: MTProto-юзербот, не Bot API. Это
единственный способ читать приватные каналы, в которых состоит
пользователь, а не только каналы, куда бот добавлен явно — ровно поэтому
продукт подключается напрямую к аккаунту пользователя, а не действует от
имени отдельного бота.

### Риск автоматизации через пользовательский аккаунт

Согласно API Terms of Service Telegram, прямо запрещено "совершать действия
от имени пользователя без его ведома и согласия" — то есть обязательное
условие легитимности подхода: пользователь сам, осознанно подключает свой
аккаунт (что и происходит по дизайну продукта — это его собственное
действие, не скрытая автоматизация). Отдельно ToS запрещает использовать
данные, полученные через API, для обучения/дообучения ИИ-моделей — наш
кейс (разовая суммаризация текста через Gemini как inference, не обучение
модели) под это ограничение не подпадает, но использовать накопленный
корпус постов для дообучения собственных моделей в будущем — нельзя без
отдельного разбора этого вопроса.

Отдельно от буквы ToS — практический риск: автоматизация через
пользовательский (не бот-) аккаунт статистически повышает шанс временных
ограничений от антиспам-систем Telegram, независимо от добросовестности
использования. Уже запланированные меры (резидентные прокси, спуфинг
имени устройства, джиттер между опросами, health-мониторинг по типам
ошибок) — это и есть смягчение этого риска, они остаются в силе и
приобретают больший вес, когда речь идёт не об одном аккаунте автора, а о
множестве аккаунтов реальных пользователей. Стоит явно предупреждать
пользователя при подключении аккаунта, что риск ограничений не нулевой.

## 5. База данных: многопользовательская модель

### 5.1 Почему меняется

Текущая БД прототипа (SQLite-файл на Render) — однопользовательская:
таблицы `channels`/`posts` глобальные, юзербот работает под одним
`SESSION_STRING` из `.env`, который задаёт разработчик руками. Для
продукта, где каждый конечный пользователь подключает свой Telegram-
аккаунт, это не подходит — нужно хранить и разграничивать данные многих
аккаунтов, их персональные фильтры и списки каналов.

### 5.2 Выбор хранилища

Требование прежнее: максимально дёшево (вплоть до бесплатного), но
**надёжно хранит данные постоянно** — это ключевое отличие от прежнего
выбора. Бесплатный диск на Render для этой роли не подходит: он
эфемерный и стирается при каждом редеплое, а начиная с 20 мая 2024 года
бесплатные управляемые PostgreSQL-инстансы самого Render истекают через
**30 дней** (было 90), после чего даётся 14 дней на переход на платный
тариф — иначе данные удаляются. Для базы, где живут чужие подключённые
аккаунты, это неприемлемо в принципе, не только неудобно.

Сравнение актуальных бесплатных вариантов с постоянным хранением:

| Вариант | Лимит хранилища | Поведение в простое | Комментарий |
|---|---|---|---|
| Render Postgres (free) | — | **истекает через 30 дней** | не подходит, см. выше |
| Supabase (free) | 500 МБ | **приостанавливается после 1 недели простоя** | риск при низком трафике на старте |
| Neon (free) | 0.5 ГБ / проект | scale-to-zero, но возобновление мгновенное, простоев по времени нет | жизнеспособный Postgres-вариант |
| CockroachDB (free) | 10 ГиБ | с сентября 2026 переведён на модель триал-кредита, а не бессрочный free-тир | не подходит под "бесплатно навсегда" |
| **Turso (libSQL)** | **5 ГБ**, 500М чтений/мес, 10М записей/мес | простоев/пауз не описано | **выбор** |
| Cloudflare D1 | 5 ГБ | лимиты суточные (5М чтений/день, 100К записей/день) | требует Cloudflare Workers-рантайм, лишняя миграция платформы |

**Решение: Turso.** Причины, помимо таблицы выше: текущий код уже написан
под SQL-диалект SQLite (`node:sqlite`, `INSERT OR IGNORE`, синхронные
prepared statements) — Turso это тот же SQLite (форк-движок libSQL),
миграция кода минимальна по сравнению с переходом на Postgres (не нужно
переписывать запросы под другой диалект). Клиент — пакет `@libsql/client`,
подключение через `createClient({ url, authToken })`; при этом `url`
может указывать как на локальный файл (`file:./data/app.db` — для
разработки и тестов, без сети и без затрат), так и на удалённую Turso-базу
(для прода) — переключение окружением, без раздвоения кода между dev и
prod. Neon остаётся задокументированной запасной опцией, если позже
понадобятся возможности реляционной модели, которых нет у SQLite.

### 5.3 Схема данных

```sql
-- Продуктовый пользователь (сейчас 1:1 с telegram_accounts,
-- разделены заранее — если появится веб-логин отдельно от Telegram
-- или несколько аккаунтов на пользователя, не потребуется миграция).
CREATE TABLE users (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at    INTEGER NOT NULL,
  status        TEXT NOT NULL DEFAULT 'active', -- active | paused | banned
  last_active_at INTEGER
);

-- Подключённый Telegram-аккаунт пользователя.
CREATE TABLE telegram_accounts (
  id                        INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id                   INTEGER NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,
  telegram_user_id          INTEGER NOT NULL UNIQUE, -- открытый ID, не секрет
  phone_number_encrypted    TEXT NOT NULL,           -- см. 5.4
  session_string_encrypted  TEXT NOT NULL,           -- см. 5.4
  session_status            TEXT NOT NULL DEFAULT 'active', -- active | needs_reauth | revoked
  connected_at              INTEGER NOT NULL,
  session_last_used_at      INTEGER
);

-- Сохранённые темы/фильтры пользователя — замена одноразового
-- свободного текста на постоянный профиль интересов.
CREATE TABLE topics (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id      INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  label        TEXT NOT NULL,      -- то, что ввёл пользователь
  is_active    INTEGER NOT NULL DEFAULT 1,
  created_at   INTEGER NOT NULL,
  last_run_at  INTEGER
);

-- Каналы, которые смотрит конкретный пользователь (публичные и приватные).
CREATE TABLE user_channels (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id            INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  channel_identifier TEXT NOT NULL, -- @username для публичных, internal id для приватных
  channel_title      TEXT,
  is_private         INTEGER NOT NULL DEFAULT 0,
  is_active          INTEGER NOT NULL DEFAULT 1,
  added_at           INTEGER NOT NULL,
  UNIQUE(user_id, channel_identifier)
);

-- Публичные посты — общий кэш на всех пользователей (дедуп, экономия
-- запросов и токенов ИИ): текст одного и того же публичного поста
-- одинаков независимо от того, чей аккаунт его прочитал.
-- Это фактически существующие channels/posts из прототипа.
CREATE TABLE public_posts (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  channel_username  TEXT NOT NULL,
  message_id        INTEGER NOT NULL,
  text              TEXT NOT NULL,
  posted_at         INTEGER NOT NULL,
  fetched_at        INTEGER NOT NULL,
  UNIQUE(channel_username, message_id)
);

-- Посты приватных каналов — НЕ общий кэш, привязаны к пользователю,
-- чьим аккаунтом получены: делиться этими данными между пользователями
-- нельзя, даже если два пользователя состоят в одном приватном канале
-- (нет гарантии, что оба должны иметь доступ к данным, полученным не
-- их собственным аккаунтом).
CREATE TABLE private_posts (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id            INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  channel_identifier TEXT NOT NULL,
  message_id         INTEGER NOT NULL,
  text               TEXT NOT NULL,
  posted_at          INTEGER NOT NULL,
  fetched_at         INTEGER NOT NULL,
  UNIQUE(user_id, channel_identifier, message_id)
);

-- Журнал активности аккаунта — основа health-мониторинга по типам
-- ошибок (уже согласованная идея) и контроля частоты использования
-- по анти-бан соображениям.
CREATE TABLE activity_log (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id      INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  event_type   TEXT NOT NULL, -- fetch_cycle | auth | error | rate_limited
  detail       TEXT,          -- короткий текст/JSON, без чувствительных данных
  occurred_at  INTEGER NOT NULL
);
CREATE INDEX idx_activity_log_user ON activity_log(user_id, occurred_at);
```

Существующие `channels`/`posts` из прототипа соответствуют новым
`user_channels`/`public_posts` — при реализации это миграция состава
таблиц, а не создание с нуля.

### 5.4 Хранение чувствительных данных

`session_string` — по сути полный доступ к Telegram-аккаунту пользователя,
`phone_number` — персональные данные. Оба поля хранятся только в
зашифрованном виде, никогда открытым текстом ни в БД, ни в логах, ни в
ответах API.

Схема шифрования (осознанно простая — платный KMS на этом этапе не
оправдан, но подход стандартный и не самодельный):

- Алгоритм: **AES-256-GCM** через встроенный `node:crypto` — ничего
  дополнительного ставить не нужно, шифр с аутентификацией (защищает и от
  подмены зашифрованных данных, не только от чтения).
- Ключ шифрования: один 32-байтный секрет (`openssl rand -base64 32`),
  хранится **только** как переменная окружения хостинга (Render
  Environment), никогда в БД и никогда в git — именно поэтому БД и ключ
  физически разделены: утечка одной Turso-базы без ключа бесполезна
  для атакующего.
- В колонке хранится одна строка вида `iv:authTag:ciphertext` (все части
  в base64) — расшифровка тривиально разбирает её на составляющие.
- Операционная оговорка: потеря ключа равносильна потере всех подключённых
  аккаунтов сразу (расшифровать станет нечем) — ключ нужно бэкапить
  отдельно и надёжно (менеджер паролей и т.п.), не полагаясь только на
  Render.

### 5.5 Что кэшировать и стирать по окончании использования, а что хранить постоянно

Это прямой ответ на вопрос "к каким данным это применимо": в проекте по
факту два разных понятия "сессии", и правило для каждого своё.

**Хранить постоянно, только в зашифрованном виде (раздел 5.4):**
`session_string`, `phone_number`, список каналов, темы/фильтры,
журнал активности. Без постоянного хранения `session_string` фоновая
работа невозможна в принципе — пользователю пришлось бы заново
авторизовываться при каждом визите, что противоречит самой идее
"подключил один раз — дальше просто приходят алерты".

**Никогда не хранить дольше одной операции, только в памяти процесса:**
- Расшифрованное (plaintext) значение `session_string` — расшифровывается
  непосредственно перед созданием клиента teleproto на время одного цикла
  чтения и не сохраняется ни в какую переменную дольше этого цикла. Это и
  есть техническая реализация идеи "взяли на сессию, применили, стёрли" —
  она применима именно к расшифрованной форме, не к зашифрованной записи
  в БД.
- Временные артефакты первичной авторизации: `phone_code_hash`, код
  подтверждения, пароль двухфакторной аутентификации при первом
  подключении аккаунта (magic-link флоу). Это одноразовые данные с очень
  коротким временем жизни — держать их в `Map` в памяти процесса с TTL в
  несколько минут и автоочисткой, либо сразу удалять после успешного/
  неуспешного завершения флоу. На один инстанс Render этого достаточно и
  бесплатно; если позже появится несколько инстансов приложения — этот
  же паттерн переносится в Redis с `EX`, без изменения логики.
- Веб-сессия самого пользователя в интерфейсе (если/когда появится вход
  в сам сервис отдельно от Telegram-аккаунта) — обычный короткоживущий
  JWT или подписанная cookie, не связана с Telegram-сессией и не требует
  отдельного проектирования сейчас.

### 5.6 Риски

- **Потеря ключа шифрования** — безвозвратная потеря доступа ко всем
  сохранённым аккаунтам разом. Смягчение: отдельный защищённый бэкап
  ключа вне Render.
- **Утечка `private_posts` между пользователями** — исключается на уровне
  схемы (везде обязательный `user_id` в паре с уникальным ограничением),
  но при написании запросов критично всегда фильтровать по `user_id`,
  не полагаться только на `channel_identifier`.
- **Ограничения на аккаунт пользователя со стороны Telegram** — см.
  раздел 3; мера — существующий анти-бан дизайн плюс явное предупреждение
  пользователя при подключении аккаунта.
- **Turso — сравнительно новый и менее проверенный временем инфраструктурный
  провайдер**, чем Postgres-гиганты. Смягчение — код БД-слоя стоит держать
  максимально тонким и стандартным SQL (как сейчас), чтобы миграция на
  Neon/другой Postgres-совместимый вариант при необходимости осталась
  быстрой правкой одного модуля, а не переписыванием бизнес-логики.

### 5.7 Что сознательно не входит в этот этап

- Проактивная фоновая рассылка алертов без действия пользователя — см.
  оговорку в разделе 2 про сон Render free-тира; текущая модель
  остаётся "пользователь открыл интерфейс — получил дайджест".
- Миграция существующих строк `channels`/`posts` из старой
  однопользовательской схемы в новую — потребуется одноразовый скрипт
  переноса при внедрении, не описан здесь детально, это задача
  реализации.

## 6. Стоимость на текущем этапе

Все выбранные компоненты остаются в рамках бесплатных тарифов при
ожидаемой на этом этапе нагрузке: Render free (хостинг), Turso free —
5 ГБ и десятки миллионов операций в месяц с большим запасом под старт,
Gemini API в рамках уже используемого ключа. Ближайший вероятный порог,
после которого что-то станет платным, — рост числа активных
пользователей до уровня, когда Render free-тир перестанет справляться
по CPU/памяти или понадобится постоянно работающий процесс (см. 5.7) —
это станет заметно по метрикам самого Render, не требует
предварительного решения сейчас.
