## Задача (ТЗ пользователя, полностью)

Нужен один общий Telegram-бот, который каждому пользователю пишет в личку.

1. **Привязка.** На `/start` взять `ctx.from.id` и найти среди пользователей,
   подключивших личный аккаунт через MTProto (`telegram_accounts.telegram_user_id`).
   Нашёл — сохранить chat_id и ответить «Готово, алерты по N темам будут
   приходить сюда». Не нашёл (зашёл с другого аккаунта) — запасной путь: на
   сайте кнопка «Получать алерты» → ссылка `t.me/<бот>?start=<токен>`, токен
   одноразовый, живёт 15 минут. На сайте показать, подключён бот или нет.
2. **Режим бота** — переменная `BOT_MODE` = `webhook` | `polling`. Сейчас
   webhook (на Render входящий запрос будит сервис), переключение без правок кода.
3. **Отправка через очередь в БД.** Поиск кладёт готовый отчёт со статусом
   `pending`, отдельный цикл разбирает и отправляет. Зависшие в `sending`
   дольше 5 минут → обратно в `pending`. Лимиты: не больше 1 сообщения/с в
   один чат и ~25/с всего. 429 → ждать `retry_after`; 403 → пометить получателя
   неактивным; прочие ошибки — 3 повтора с паузой, затем `failed`.
4. **my_chat_member** — знать, когда пользователь заблокировал/разблокировал
   бота, и не слать зря.
5. **Интерфейс `Notifier.send`.** Сейчас только Telegram; потом почта для
   компаний — должна добавляться одним классом.
6. **Без повторов.** Таблица обработанных постов: подписка, канал, id сообщения.
   Если нового нет — ничего не слать, только сдвинуть время последней проверки.
   Один вызов LLM на всю подписку, а не на пост.
7. **Тихие часы** (уже есть) — обычные отчёты копятся и потом приходят одним
   сообщением.
8. **Никакой дезинформации.** LLM отвечает строго JSON: каждый пункт — текст +
   список id постов-источников. Низкая temperature; в промпте: только по
   переданным постам, ничего от себя, противоречия источников так и называть.
   Код проверяет каждый пункт (см. «Проверка пунктов»). Не прошёл — выкинуть и
   залогировать. Не прошёл ни один — отчёт не слать.
9. **Формат.** HTML, текст модели обязательно экранировать. Сверху тема и время,
   под каждым пунктом ссылка на оригинальный пост. Длиннее 4096 — резать на
   части по пунктам. Под алертом кнопки «Не релевантно», «Реже», «Отключить
   тему»; нажатия — в отдельную таблицу.
10. **Громкие и тихие.** LLM в том же JSON ставит срочность. Срочное — со
    звуком, остальное — `disable_notification`. Порог пользователь выбирает.
    Режим дайджеста: обычные копятся и приходят раз в N часов.
11. **В боте только быстрые настройки:** `/topics` (список тем, кнопки
    вкл/выкл), пауза на час или до утра, частота проверки, порог срочности,
    кнопка «Настройки» (пока ведёт на сайт).
12. **Отвалилась личная MTProto-сессия** — бот пишет со ссылкой на
    переподключение (детали в решении 5 ниже).

**Заложить, но сейчас не делать:**
- «Настройки» откроет сайт как Mini App внутри бота с авторизацией по
  `initData` (без отдельного логина).
- Для компаний: бота добавляют в рабочую группу через `/connect <токен>`;
  если в группе есть темы (forum topics), каждая подписка уходит в свою тему
  через `message_thread_id`.

## Решения пользователя по спорным пунктам

1. **Подписка = тема + в каких каналах ищем + свои настройки** (частота,
   тихие часы, порог срочности и т.д.). То есть настройки — у каждой подписки
   свои, а не один набор на пользователя. Текущие `topics` + общий
   `alert_settings` нужно перевести на подписки (миграция существующих тем:
   каждая получает копию текущих настроек пользователя) и переделать вкладку
   «Алерты» на сайте под список подписок.
2. **Дайджест — «раз в N часов»** (вместо нынешнего «раз в день в ЧЧ:ММ»).
3. **Срочное пробивает тихие часы.**
4. **Срочность — три уровня** от модели (например обычное/важное/срочное),
   пользователь выбирает, с какого уровня со звуком. Никаких шкал 0–100.
5. **Отвалилась личная сессия:** публичные каналы продолжают проверяться
   (их читает общий аккаунт). На паузу встают только приватные каналы:
   - в подписке есть и публичные, и приватные → работает по публичным, внизу
     алерта пометка «приватные каналы сейчас не проверяются, переподключите
     аккаунт» (со ссылкой);
   - подписка целиком из приватных → полностью на паузе;
   - отдельное предупреждение со ссылкой — не чаще раза в сутки, напоминать
     через сутки, пока не переподключится.
6. **Кнопки под алертом:**
   - «Отключить тему» — сразу; бот отвечает «Тема отключена» + кнопка
     «Включить обратно»;
   - «Реже» — сразу увеличивает интервал на шаг и пишет в таблицу; ответ
     «Теперь проверяю раз в N» + кнопка отмены; на максимальном шаге —
     «реже уже нельзя»;
   - «Не релевантно» — только запись в таблицу.
7. **Пауза «до утра»** = до 09:00 МСК; если нажали после 09:00 — до 09:00
   следующего дня. В ответе — точное время окончания паузы. Найденное за
   время паузы обрабатывать так же, как в тихие часы (одна логика).
   ✅ Решено (новый чат, 14.10.2026): срочное пробивает и паузу тоже — одна
   логика с тихими часами. Пауза из бота действует на все подписки сразу.
8. **Сделано в прошлом чате:** старт сервера больше не пишет общий аккаунт
   как «личный» пользователю #1 (`removeSharedSessionDuplicate` в
   `bootstrap.ts`), дубль в локальной БД удалён. Сессия общего аккаунта
   проверена — жива (telegram id 613057479). Пользователь потом подключит
   свой личный аккаунт через сайт, как все.

## Решения, принятые при реализации (новый чат)

- **Подписка = строка `topics`**, а не новая таблица `subscriptions`: к `topics`
  добавлены `settings_json` и `destination_id`, `last_run_at` = время последней
  проверки. id тем сохраняются, переносить данные не нужно. Общий
  `alert_settings` при старте копируется в каждую тему пользователя и
  удаляется (`migrateAlertSettingsToTopics` в `database.ts`); старый общий
  выключатель складывается с вкл/выкл темы, дайджест «в ЧЧ:ММ» → «раз в 24 ч».
  Таблица обработанных постов — `topic_seen_posts`.
- **Пауза хранится у получателя** (`alert_destinations.paused_until`), а не у
  подписки: «на все сразу» — одно поле; в группе компании `/pause` заглушит
  только эту группу.
- **`destination_id` NULL = личный чат пользователя с ботом**; явная ссылка
  нужна только для группы компании.
- **«Срочное» = срочность ≥ порога пользователя** (`loudFrom`: normal /
  important / urgent, по умолчанию urgent): такой отчёт идёт со звуком и
  сквозь тихие часы, паузу и дайджест; остальные — без звука и копятся.
  Громкое не упирается и в дневной лимит (одно правило: «громкое приходит всегда»).
- **Склейка придержанного — по подписке**, а не по получателю целиком: у
  сообщения одна тема в шапке и осмысленные кнопки «Реже / Отключить тему».
  Три темы после тихих часов = три сообщения.
- **Задержка пересчитывается при выпуске** (`holdPolicy.holdUntil`): если после
  создания отчёта поставили паузу или ушёл лимит — отчёт ждёт дальше.
- **Окно постов подписки** — `topics.checked_until` (двигается только при
  успешной проверке; первая проверка — за интервал), не дальше суток назад.
  `last_run_at` — любая попытка, по нему расписание. Упал LLM — повтор через
  интервал с теми же постами.
- **Замок одного экземпляра** (`service_locks`, lease 60 с, продление раз в
  20 с): порт открывается сразу (иначе Render не дождётся health check при
  деплое), а MTProto общего аккаунта, polling бота и планировщик стартуют
  только после захвата замка. До этого запросы сайта к Telegram получают
  ошибку «disconnected» (teleproto сам не подключается). Потерял замок —
  процесс штатно останавливается.
- Keyword-фильтр прототипа — подстрока темы («ставка» не найдёт «ставку»);
  ничего не совпало — в LLM уходят все новые посты (как в поиске).

## Согласованные улучшения

- **Проверка пунктов (п. 8 ТЗ), делаем так:**
  - каждый пункт проверяется только по постам, на которые он ссылается;
  - все `source_ids` должны быть среди переданных модели;
  - числа сравниваются как значения, а не строки: `1,5` = `1.5`, пробелы и
    неразрывные пробелы в разрядах убираются; каждое число из пункта должно
    найтись среди чисел цитируемых постов;
  - к каждому пункту модель даёт короткую дословную цитату из поста — код
    проверяет, что она реально там есть (нормализация пробелов и регистра);
  - даты/время модели не даём и писать не разрешаем — время поста
    подставляем сами из метаданных (так уже сделано сейчас).
- **Помнить все обработанные посты** (не только отправленные) — с флагом
  «отправлен», чтобы нерелевантное не уходило в LLM повторно. Брать посты с
  момента последней проверки подписки, но не дальше 24 часов назад.
- **Задел «куда доставлять»:** отдельная таблица получателей (тип: личка /
  группа / почта; chat_id, thread_id, email, статус). Подписка ссылается на
  получателя; `Notifier.send(получатель, сообщение)`. Группа компании и почта —
  новые типы получателя + один класс Notifier. В группах Telegram — не больше
  20 сообщений в минуту, учесть в лимитере.
- Токен для `?start=` хранить в БД **хешем** (не в памяти — на Render процесс
  засыпает). Payload `start` — до 64 символов `[A-Za-z0-9_-]`.
- Webhook проверять по `secret_token` (заголовок
  `X-Telegram-Bot-Api-Secret-Token`).
- Библиотека бота — **grammY** (одна зависимость, TypeScript, webhook+polling,
  callback-кнопки, `my_chat_member`). Очередь, лимиты и повторы — свои, как в ТЗ.
- **Замок одного экземпляра** (предложено, явно не отклонено — делать): при
  старте брать lease в БД, чтобы MTProto-клиенты и планировщик работали только
  в одном процессе (при деплое Render старый и новый инстанс какое-то время
  живут вместе → риск `AUTH_KEY_DUPLICATED`).

## Инфраструктура (решение пользователя) и честные ограничения

- Остаёмся на бесплатном Render, **без пингов и прочих обходных путей**;
  позже переезд на платный хостинг.
- Следствие, о котором пользователь знает: на free Render процесс засыпает
  через ~15 минут без HTTP-трафика — плановые проверки в это время не идут,
  алерты придут, когда сервис проснётся. Webhook будит сервис только при
  сообщении боту.
- Диск free Render стирается при деплое: очередь, привязки, история — теряются,
  пока не подключён Turso. Для прода алертов Turso обязателен.
- «Не уйдёт дважды» строго не гарантируется: если упасть после того, как
  Telegram принял сообщение, но до отметки `sent`, через 5 минут оно уйдёт
  повторно (у Bot API нет ключа идемпотентности). Это редкий случай,
  пользователь проинформирован.
- Локально webhook не работает (нужен публичный HTTPS) → локально
  `BOT_MODE=polling`. Polling в двух процессах одновременно даёт 409 Conflict.
- Gemini не отвечает с российских IP («User location is not supported»):
  ИИ-шаг локально проверять только через VPN с проверенным иностранным IP
  (ipinfo.io) или на Render. Смена модели не помогает.
- Квота Gemini: вызов на подписку за проверку. 10 пользователей × 3 подписки ×
  24 проверки ≈ 720 вызовов/сутки — около бесплатного дневного лимита
  flash-lite. Пока ок, при росте — упрётся в квоту.

## Циклы и поток данных

1. **Планировщик** (раз в минуту): подписки, у которых подошло время →
   группировка по пользователю → fetch каналов ОДИН раз на пользователя
   (публичные — общий аккаунт, приватные — личный; при ошибке сессии →
   `needs_reauth`) → по каждой подписке: новые посты её каналов → keyword-
   фильтр → ОДИН вызов LLM → проверка пунктов → если валидных пунктов
   ≥ minMatches — отчёт → решить: в очередь сейчас или придержать (тихие часы,
   пауза, дайджест, дневной лимит; срочное пробивает тихие часы) → отметить
   посты обработанными → сдвинуть last_checked_at.
2. **Выпуск придержанного:** когда закончилась задержка — склеить
   накопленные отчёты получателя в одно сообщение → в outbox.
3. **Отправщик** (частый тик): берёт pending с учётом лимитов (1/с на чат,
   ~25/с всего, 20/мин на группу) → `sending` + locked_at →
   `Notifier.send` → `sent` / повтор / `failed`; зависшие > 5 мин → `pending`.
4. **Напоминание о переподключении** — раз в сутки на пользователя.

Существующий `analyzeTopic` перестроить: fetch отдельно от анализа (сейчас
он фетчит внутри для каждой темы). `POST /api/alerts/preview` перевести на
тот же конвейер (сухой прогон без отправки).

## Ответ LLM (черновик схемы)

`{ items: [{ text, source_ids: number[], quote, urgency: "normal" | "important" | "urgent" }] }`
— срочность отчёта = максимум по прошедшим проверку пунктам. Temperature
0–0.1. Промпт: только по переданным постам, ничего от себя, противоречия
называть явно со ссылками на оба поста, числа переписывать в том виде, как в
источнике, дат и времени не писать. Схема остаётся в `geminiClient.ts`
(одна точка вызова LLM).

## Бот: команды и кнопки

- `/start [токен]` — привязка (п. 1); ответ с числом активных подписок.
- `/topics` — список подписок с кнопками вкл/выкл.
- Пауза: «на час» / «до утра» (09:00 МСК, см. решение 7), ответ с точным временем.
- Частота проверки и порог срочности — выбор из кнопок.
- «Настройки» — URL-кнопка на сайт (`PUBLIC_BASE_URL`), позже Mini App.
- Кнопки под алертом: только под последней частью разбитого сообщения;
  `callback_data` ≤ 64 байт (например `fb:off:<subId>`, `undo:less:<subId>:<prev>`).
- Шаги «Реже» — по пресетам интервала 15 мин → 30 мин → 1 ч → 3 ч → 5 ч → 10 ч → 24 ч.
- `my_chat_member`: `kicked` → получатель `blocked`; `member` → `active`.

## Что нужно от пользователя (переменные окружения)

- Создать бота в @BotFather → токен.
- `.env` и Render → Environment:
  - `TELEGRAM_BOT_TOKEN` — токен бота;
  - `BOT_MODE` — `polling` локально, `webhook` на Render;
  - `PUBLIC_BASE_URL` — адрес сайта на Render (для webhook и ссылок);
  - `TELEGRAM_WEBHOOK_SECRET` — случайная строка (`openssl rand -hex 32`).
  Добавить их в `.env.example` с описанием (без значений).

## План (коммит после каждого этапа)

1. Схема БД + миграция тем/настроек в подписки (+ тесты).
2. LLM-отчёт с источниками + валидатор пунктов — чистые функции, много тестов
   (числа, цитаты, чужие id, «ни один не прошёл → не слать»).
3. Формирование сообщения: HTML-экранирование, шапка, ссылки, нарезка ≤ 4096
   по пунктам, клавиатура (+ тесты).
4. Outbox + отправщик + `Notifier` + `TelegramNotifier`: лимиты, 429/403/повторы,
   возврат зависших (тесты с фейковым notifier и часами).
5. Бот на grammY: BOT_MODE, webhook с secret, `/start` (id + токен),
   `my_chat_member`, кнопки обратной связи и отмены, быстрые команды.
6. Планировщик: подписки по времени, один fetch на пользователя, обработанные
   посты, придержка (тихие часы / пауза / дайджест / лимит, срочное пробивает),
   переподключение сессии + ежедневное напоминание, замок одного экземпляра.
7. Сайт: вкладка «Алерты» — список подписок со своими настройками, кнопка
   «Получать алерты», статус бота, порог срочности, дайджест N часов.
8. Документация (`CLAUDE.md`, `.env.example`, README) + ручная проверка:
   локально polling (+ VPN для ИИ) или на Render.

## Грабли проекта (уже наступали)

- Никогда не убивать сервер жёстко (`taskkill /F`, `kill -9`) — MTProto-сессия
  не закрывается, Telegram отвечает `AUTH_KEY_DUPLICATED` и убивает сессию.
  Сервер останавливать штатно; две копии одновременно не запускать.
- Не импортировать `src/config/botConfig.ts` в новых модулях, которые
  подтягивают тесты: он на импорте вызывает `dotenv.config()` и бросает без
  API_ID — ломал изоляцию тестов. Читать `process.env` напрямую.
- Засев тестовых данных через `curl` в консоли Windows портит кириллицу —
  засевать через node/fetch или интерфейс.
- CSS: есть глобальное `[hidden] { display: none !important; }` — не убирать.
- Тесты в `package.json` перечислены явно; новый файл — дописать.
- Кириллица в путях (`Рабочий стол`) — в bash-скриптах путь в кавычках.
