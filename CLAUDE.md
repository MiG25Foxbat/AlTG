# gram-pervonah — Telegram AI-алертер (прототип)

> **Алерты через общего Telegram-бота (октябрь 2026)** — реализованы по
> плану из `docs/handoff-telegram-alerts-bot.md` (ТЗ, решения пользователя,
> принятые при реализации решения, текущее состояние). Ветки `alerts/<N>-…`
> идут цепочкой; в `main` сливаются по просьбе пользователя.

Что это: Telegram-юзербот, который читает посты из публичных каналов за
выбранный период, фильтрует их по свободной теме, которую вводит
пользователь, и присылает ИИ-саммари вместо того, чтобы читать каналы
руками. Управление — через локальный HTML-интерфейс (`public/`), без
Telegram Mini App (это в планах, не реализовано). С регистрацией по
логину/паролю: каждый веб-аккаунт хранит свой список каналов, Telegram-
подключение при этом одно общее (см. "Аутентификация" ниже).

Полный бизнес-контекст, целевая (будущая) архитектура и история решений —
в `docs/project-context.md`. Финальный принятый техстек и подробная
архитектура БД под многопользовательскую модель (каждый пользователь
подключает свой Telegram-аккаунт) — в `docs/tech-stack-final.md`, это
источник истины по актуальным решениям. `docs/tech-stack-review.md` —
более старая ревизия стороннего техстека, оставлена для истории. Читать
по необходимости, не обязательно в каждой сессии.

## Происхождение кода

Форк/переделка `github.com/litury/gram-pervonah` — изначально это был бот
для авто-реакций и авто-комментариев в чужих каналах. Функции реакций и
комментариев (`src/modules/CommentModule/`, реакции в `UserBot.ts`)
закомментированы/отключены, не удалены — на случай, если понадобятся
позже. Не включать их обратно без явного запроса.

## Важное расхождение с ранее планировавшейся архитектурой

Это сознательно **упрощённый прототип**, а не отказ от прежнего плана.
Что упрощено по сравнению с целевой архитектурой (детали в
`docs/project-context.md`):

- Node.js + ts-node, а не Bun
- Только публичные каналы через MTProto (GramJS), нет RSS-гибрида
- Двухступенчатый фильтр в ручном поиске (keyword → фолбэк на полный
  ИИ-анализ корпуса), а не трёхслойный (keyword → эмбеддинги → LLM). В алертах
  фильтра по словам нет: все новые посты темы уходят в модель, по смыслу решает она
- Одна основная модель — Mistral (`mistral-medium-latest`) с резервом Groq
  (`openai/gpt-oss-120b`), а не продуманная мульти-провайдерная схема
- Render, а не Railway
- Ручной `SESSION_STRING` через `.env`, а не magic-link реавторизация

Цель прототипа — проверить, достаточно ли простой связки
"keyword-фильтр + одна ИИ-модель" по качеству, прежде чем вкладываться в
трёхслойный пайплайн. Не "упрощай ещё сильнее" и не "давай сразу строй
целевую архитектуру" без явного запроса пользователя — сейчас стадия
тестирования гипотезы.

## Стек и команды

- Рантайм: Node.js >=22.13.0, TypeScript, `ts-node` (без сборки для
  разработки; `npm run build` → `tsc` → `dist/` только для прод-запуска)
- Backend: Express 5
- БД: **`@libsql/client`** (Turso/libSQL) — многопользовательская схема
  (`users`/`telegram_accounts`/`topics`/`user_channels`/`public_posts`/
  `private_posts`/`activity_log`), подробности в `docs/tech-stack-final.md`.
  `url` — локальный файл (`DB_PATH`, по умолчанию) или `TURSO_DATABASE_URL`
  для прода; `telegram` (GramJS) заменён на `teleproto` (GramJS
  заархивирован, см. раздел "Известные грабли")
- Telegram: `teleproto` (GramJS форк), MTProto-юзербот, не Bot API
- ИИ: цепочка OpenAI-совместимых API через голый `fetch` (без SDK) —
  Mistral первым, Groq резервом; весь код вызова ИИ — в
  `src/modules/AiModule/llmClient.ts` (очередь Mistral ≤ 1 запрос/с —
  `MISTRAL_MIN_INTERVAL_MS`; 429 → retry-after или 2/4/8 с, три повтора;
  таймаут 30 с и прочие ошибки → тот же запрос в Groq). Gemini убран: не
  отвечал с российских IP даже через VPN
- Frontend: чистый HTML/CSS/JS без фреймворка, `public/`
- Бот алертов: `grammy` (Bot API), режим `BOT_MODE` = `webhook` | `polling`;
  отправка алертов — своя очередь `outbox` + `TelegramNotifier` (голый fetch)

Команды:

```bash
npm install
npm run dev          # старт сервера разработки (ts-node src/server.ts)
npm run build        # tsc → dist/
npm start            # прод-запуск (тоже ts-node, см. package.json)
npm run generate-session   # разовая генерация SESSION_STRING для .env
npm test             # node:test, 133 теста
```

Тесты запускаются явным списком файлов (`node --require ts-node/register
--test <files>`), не через discovery — так исторически обошли проблему с
расширением `.ts`. При добавлении нового тестового файла его нужно
дописать в `scripts.test` в `package.json`, иначе он не запустится.

## Аутентификация

Веб-логин (username/password) — это отдельный слой поверх уже существующей
многопользовательской схемы, не переделка Telegram-интеграции:

- **Один общий Telegram-бот** (`SESSION_STRING` из `.env`, как и раньше) читает
  публичные каналы; он не привязан персонально к каждому веб-пользователю.
- **Каждый веб-аккаунт** (таблица `users`, колонки `username`/`password_hash`,
  добавлены поверх исходной схемы из `docs/tech-stack-final.md`) хранит свой
  собственный список каналов (`user_channels`) — независимо от других аккаунтов.
- Пароли — `scrypt` (`utils/crypto.ts`, `hashPassword`/`verifyPassword`),
  не bcrypt/argon2: встроено в `node:crypto`, ставить нечего.
- Сессия — подписанный HMAC-токен в HTTP-only куке (`utils/session.ts`),
  не JWT-библиотека и не `cookie-parser`: то и другое — несколько строк на
  голом `node:crypto`/разборе заголовка `Cookie`. Ключ для подписи — не
  отдельный секрет, а производный от уже существующего
  `SESSION_ENCRYPTION_KEY` (`deriveKey('web-session')` в `crypto.ts`) с
  разделением по назначению через HMAC, чтобы не заводить второй секрет
  в `.env` ради этого.
- **Первая регистрация "забирает" системного пользователя.** Если на момент
  регистрации в `users` уже есть строка без `username` (тот самый системный
  юзер, к которому `bootstrap.ts` привязал Telegram-аккаунт, и под которым,
  возможно, уже сохранены каналы из однооператорского режима) — именно
  первый зарегистрировавшийся получает эту строку и её данные, а не пустой
  аккаунт с нуля (`registerUser()` в `usersRepo.ts`). Все следующие
  регистрации такую строку уже не находят и создают новую с нуля.
- Роуты `/api/register`, `/api/login`, `/api/logout`, `/api/me` — публичные;
  `/api/channels*` и `/api/analyze` — за `requireAuth` в `app.ts`.

## Личный Telegram-аккаунт пользователя и приватные каналы

Каждый веб-пользователь может дополнительно подключить свой личный
Telegram-аккаунт (`src/modules/UserBotModule/personalAccount.ts`), чтобы
мониторить закрытые каналы/группы, куда общий системный бот доступа не
имеет — это отдельный, необязательный слой поверх обычного веб-логина,
не замена ему.

- **Flow:** `POST /api/telegram/connect/start` (`client.sendCode`) →
  `POST /api/telegram/connect/code` (`Api.auth.SignIn`, может вернуть
  `needs_password` при включённой 2FA) → `POST /api/telegram/connect/password`
  (`client.signInWithPassword`). Успешный результат сохраняется через уже
  существующий `telegramAccountsRepo.upsertAccount()` — та же зашифрованная
  запись, что и для системного бота, но теперь по-настоящему за каждым
  реальным пользователем.
- **Временное состояние флоу** (`phoneCodeHash`, живое MTProto-соединение
  на время ввода кода/пароля) — только в памяти процесса, `Map<userId, ...>`
  с TTL 5 минут и автоочисткой раз в минуту (`docs/tech-stack-final.md`,
  5.5). Никогда не попадает в БД.
- **Приватные каналы находятся через `client.getDialogs()`**, а не по
  ссылке-приглашению или названию: `GET /api/telegram/private-dialogs`
  отдаёт каналы/супергруппы без публичного `@username`, в которых
  подключённый аккаунт уже состоит — надёжнее, чем парсить произвольные
  инвайт-ссылки, и не требует отдельной логики "не найден/не участник".
- **Чтение приватных постов** — через `withPersonalClient()`: расшифровка
  сессии, разовое подключение, `client.getMessages()`, отключение сразу
  после — та же дисциплина "взяли на цикл, применили, стёрли", что и для
  системного бота (5.5 дока). Пишет в `private_posts` (см.
  `privatePostsRepo.ts`), никогда в общий `public_posts`.
- **`fetchService.fetchRecentPrivatePosts()`** и обычный
  `fetchRecentPosts()` (общий бот) запускаются в `analyzeService.ts`
  параллельно (`Promise.all`), результаты из `public_posts`/`private_posts`
  объединяются перед фильтром/ИИ — с точки зрения остального пайплайна
  разницы между публичным и приватным постом больше нет.
- Отключение аккаунта (`POST /api/telegram/disconnect`) — best-effort
  `Api.auth.LogOut` на стороне Telegram, затем удаление записи из БД в
  любом случае (даже если удалённый логаут не удался).
- В интерфейсе перед подключением показывается явное предупреждение о
  риске ограничений от Telegram при автоматизации через личный аккаунт
  (`docs/tech-stack-final.md`, раздел 3) — это требование дока, не просто
  формальность.
- **Известная грабля, в которую уже попадали:** жёсткое завершение процесса
  сервера (`taskkill /F`, `kill -9`) вместо штатной остановки (`Ctrl+C`
  → `SIGINT`-хендлер в `server.ts`) может не дать MTProto-сессии закрыться
  корректно — при быстром переподключении той же `SESSION_STRING` Telegram
  иногда трактует это как конкурентное использование и аннулирует сессию
  (`AUTH_KEY_DUPLICATED`), после чего `SESSION_STRING` нужно перегенерировать
  заново (`npm run generate-session`, интерактивно, нужен доступ к телефону).
  Всегда останавливать сервер штатно.

## Группы каналов и алерты

- **Группы** (`channel_groups`, `user_channels.group_id`, `src/db/groupsRepo.ts`) —
  папки для каналов: у канала максимум одна группа; удаление группы не
  удаляет каналы (`ON DELETE SET NULL`). Все изменения групп и перенос канала
  проверяют владельца в SQL (`user_id` в WHERE / `EXISTS` для чужой группы).
- **Правило «канал мониторится»** живёт в одном месте — SQL view
  `monitored_channels` (`database.ts`): канал включён И (без группы ИЛИ группа
  включена). Через него идут списки каналов для опроса и выборки постов
  (`postsRepo`, `privatePostsRepo`, `countMonitoredChannels`). Новые выборки
  "активных каналов" — тоже только через этот view, не повторять условие.
  На фронте то же правило — `isMonitored()` в `app.js`.
- **Приватные каналы в URL**: `parseChannelParam()` — числовой id (`-100…`)
  проходит как есть, имя публичного канала нормализуется как раньше.
- **Алерты** — подробно в `docs/handoff-telegram-alerts-bot.md`. Коротко:
  - подписка = строка `topics` со своими настройками в `settings_json`
    (на входе всегда `sanitizeTopicSettings()` — граница доверия): интервал,
    область (все / группы / каналы), сводка раз в N часов, тихие часы (МСК),
    порог звука `loudFrom`, minMatches, maxPerDay. Старый общий
    `alert_settings` при старте переносится в темы и удаляется;
  - доставка — общий бот (grammY) в личку; получатель — `alert_destinations`
    (пауза там же), привязка по `/start` (Telegram id подключённого аккаунта
    или одноразовый токен, в БД хеш);
  - планировщик раз в минуту → один fetch на пользователя → по теме только
    новые посты (`topic_seen_posts`) → один вызов LLM → `validateReportItems`
    → `alert_reports` → придержка (`holdPolicy`) → `outbox` → отправщик;
  - громкое (срочность ≥ `loudFrom`) — сразу и со звуком сквозь всё,
    остальное копится и склеивается по теме;
  - `POST /api/alerts/preview` — тот же конвейер всухую.

## Правила безопасности с credentials — соблюдать всегда

`SESSION_STRING` — это фактически полный доступ к Telegram-аккаунту,
`MISTRAL_API_KEY` / `GROQ_API_KEY` — платёжный доступ к API ИИ, `SESSION_ENCRYPTION_KEY` —
ключ шифрования для конфиденциальных полей в БД. Все три:

- живут только в `.env` (в `.gitignore`) или в переменных окружения
  хостинга (Render → Environment)
- **никогда** не должны появляться в коммитах, в этом файле, в других
  документах, в выводе команд, которые могут попасть в чат/лог
- если пользователь просит что-то продиагностировать через вывод `.env`
  или переменных окружения — маскировать значения, показывать только факт
  наличия/отсутствия переменной, не сами значения

## Текущее состояние деплоя

Задеплоено на **Render** (бесплатный тариф) — не Railway, как
предполагалось в целевой архитектуре. Причина именно Render: Gemini API
не отвечал на запросы с российских IP, а Render даёт сервер за пределами
РФ (сейчас ИИ — Mistral/Groq; их ключи на Render вписываются в Environment
отдельно, локальный `.env` он не видит). Пользователь подтвердил: деплой работает, все функции протестированы
на проде.

Особенности free-тарифа Render, которые нужно держать в голове при любых
изменениях, влияющих на БД или на время отклика:

- диск эфемерный — без платного Disk файл SQLite (`data/app.db`) стирается
  при каждом редеплое
- сервис засыпает после ~15 минут неактивности, первый запрос после сна
  долгий

## Известные грабли (уже решённые — не наступать снова)

- **`better-sqlite3` на Windows падает при `npm install`** без Visual
  Studio C++ Build Tools (нативная сборка). Именно поэтому в проекте
  используется `@libsql/client` — он поставляет прекомпилированные
  бинарники под все платформы, включая Windows, и эта проблема больше не
  возникает. Не заменять на `better-sqlite3` без веской причины.
- **`gram-js/gramjs` был заархивирован 14 июля 2026 года — сделано.**
  Зависимость заменена на `teleproto` (см. `docs/tech-stack-final.md`,
  раздел 3). Импорты `from "teleproto"`, формат session string тот же.
- **`@libsql/client` в local-file режиме держит пул до 20 соединений** —
  `PRAGMA foreign_keys = ON`, выполненная через `execute()`, применяется
  только к одному соединению из пула, а не ко всем. Решено передачей
  `concurrency: 1` в `createClient()` (см. `src/db/database.ts`) — один
  коннект гарантирует, что `ON DELETE CASCADE` в схеме реально работает.
  Не убирать `concurrency: 1` без замены на другой способ применить
  pragma ко всем соединениям пула.
- **встроенные `.d.ts` из `teleproto` конфликтуют по типам с TypeScript
  5.2.2** — `Buffer` используется как generic (ошибки TS2315 в 45+ местах),
  отсутствуют алиасы типов (`InlineKeyboard`, `ReplyKeyboard` в
  `define.d.ts`). Эти ошибки всплывают на этапе разрешения модулей, поэтому
  `@ts-expect-error` над строкой импорта их не гасит; на поведение в
  рантайме они не влияют, все тесты проходят. Решение: `"skipLibCheck":
  true` в `tsconfig.json` отключает валидацию `.d.ts` для node_modules.
  Держать этот флаг — стандартный обход проблем с типизацией сторонней
  библиотеки. Не убирать без повторной проверки тайпингов `teleproto`.

- **Замок одного экземпляра (`service_locks`).** MTProto общего аккаунта,
  polling бота, планировщик и отправщик стартуют только в процессе, который
  взял lease (`server.ts`); порт открывается сразу, иначе Render не дождётся
  health check при деплое. Пока замок у другого процесса — запросы сайта к
  Telegram отвечают «disconnected» (teleproto сам не подключается). Второй
  локальный `npm run dev` будет ждать замок — это защита, не зависание.
- **libsql на Windows держит файл БД и после `close()`** — тест с временным
  файлом не смог его удалить (EPERM). В тестах только `DB_PATH=':memory:'`.
- **Keyword-фильтр — подстрока темы** («ставка» не находит «ставку») и есть
  только в ручном поиске. Из алертов убран: он пропускал к модели посты со
  словом «москве» и отсеивал «открылась кофейня» для темы «кафешки в Москве».
- **Лимиты бесплатного Groq (`openai/gpt-oss-120b`): 8000 токенов в минуту,
  1000 запросов в сутки** (заголовки `x-ratelimit-*`). Пока у Mistral лимит 0
  (`x-ratelimit-limit-req-minute: 0` — не активирован тариф), всё идёт в Groq,
  и запрос больше ~30–40 постов он отклонит.

## Тестовая стратегия проекта

Тесты специально спроектированы так, чтобы не требовать реального
Telegram-аккаунта или реального ключа ИИ:

- `IUserBotReader` — минимальный интерфейс, под который подставляется
  фейковый клиент в тестах вместо GramJS
- `windowPagination.ts` вынесена в чистую функцию именно ради
  тестируемости постраничной логики через инжектируемый фейковый
  page-fetcher
- Приоритет при добавлении новой логики — стараться держать её в чистых
  функциях с DI, а не в коде, завязанном напрямую на GramJS/ИИ/сеть,
  чтобы новую логику можно было так же покрыть тестами без реальных
  внешних вызовов
